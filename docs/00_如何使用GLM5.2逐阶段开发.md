# 如何使用 GLM-5.2 逐阶段开发

## 两个目录的作用

- `C:\Users\10156\AppData\Local\Cockpit Tools`：已经安装的成品程序，只有 EXE 和运行资源。只用于运行、观察和对照，禁止在这里开发或替换文件。
- `C:\Users\10156\Desktop\脚本\切换应用`：开发工作目录。源码、开发文档、Git 分支、测试和构建产物都放在这里。

## 第一次准备源码

在 PowerShell 中执行：

```powershell
Set-Location -LiteralPath 'C:\Users\10156\Desktop\脚本\切换应用'
git clone --branch v1.3.16 --single-branch https://github.com/jlcodes99/cockpit-tools.git source
Set-Location -LiteralPath '.\source'
git rev-parse HEAD
```

`git rev-parse HEAD` 必须输出：

```text
e1ef55ce9f158dd1ee9fd682cf8d9aa1b79601e8
```

然后执行：

```powershell
git switch -c codex/trae-work-cn-switcher
New-Item -ItemType Directory -Force -Path '.\docs' | Out-Null
Copy-Item -LiteralPath '..\TRAE_WORK_CN_SWITCHER_GLM52_DEVELOPMENT_GUIDE.md' -Destination '.\docs\TRAE_WORK_CN_SWITCHER_GLM52_DEVELOPMENT_GUIDE.md' -Force
npm install
npm run typecheck
cargo test -p cockpit-tools
npm run tauri dev
```

原版窗口成功打开后，关闭开发程序。阶段 0 才算完成。

## 每个阶段如何使用 GLM-5.2

不要说“根据文档把整个软件做完”。每次只做一个阶段。

推荐每个阶段开启一个新对话，并把 GLM 的工作目录设置为：

```text
C:\Users\10156\Desktop\脚本\切换应用\source
```

每个新对话先发送：

```text
请先读取：
docs/TRAE_WORK_CN_SWITCHER_GLM52_DEVELOPMENT_GUIDE.md

严格遵守文档第 0 节的最高优先级指令。
桌面实际编译的是 src-tauri/src/modules 下的代码，不要只修改 crates/cockpit-core。
内部继续使用 TraePlatformKind::TraeSoloCn 和 trae_solo_cn，不要新增 trae_work_cn 平台。
不要输出任何真实 Token、refresh token、设备私钥或 GitHub secret。

本次只执行“阶段 N：阶段名称”。禁止提前实现后续阶段。
开始修改前：
1. 检查 git status；
2. 阅读该阶段涉及的上游文件；
3. 列出修改计划和具体文件；
4. 先写或补测试，并运行确认测试失败；
5. 再进行最小实现；
6. 运行文档指定的全部验证命令；
7. 给出实际命令、退出码、测试结果、git diff --stat 和仍存在的问题。
如果验证失败，不得声称阶段完成，不得进入下一阶段。
```

将 `N：阶段名称` 替换为当前阶段，例如：

```text
本次只执行“阶段 1：品牌和应用壳收敛”。禁止提前实现后续阶段。
```

## 阶段顺序

1. 阶段 0：建立干净基线——主要由你在终端执行，不让 GLM 修改业务代码。
2. 阶段 1：品牌和应用壳收敛。
3. 阶段 2：Work CN 路径和安装发现兼容。
4. 阶段 3：完整账号快照导入。
5. 阶段 4：安全的一键切换和回滚。
6. 阶段 5：积分查询和展示。
7. 阶段 6：GitHub Secrets 槽位同步。
8. 阶段 7：四账号完整体验和后台会话同步。
9. 阶段 8：清理、发布和安装包。

## 一个阶段结束后你必须做什么

不要只相信 GLM 的“已完成”。在 PowerShell 中自己执行：

```powershell
Set-Location -LiteralPath 'C:\Users\10156\Desktop\脚本\切换应用\source'
git status --short
git diff --stat
git diff
npm run typecheck
npm run build
cargo test -p cockpit-tools
```

涉及桌面运行时，再执行：

```powershell
npm run tauri dev
```

人工确认该阶段功能后才提交：

```powershell
git add -A
git commit -m '阶段对应的英文提交信息'
```

建议每阶段完成后打本地标签：

```powershell
git tag work-cn-stage-1
git tag work-cn-stage-2
```

标签数字按阶段变化。如果后续 GLM 改坏，可以回到上一个标签检查或恢复。

## 推荐的实际对话方式

### 第一个 GLM 对话：阶段 1

发送上面的通用开场提示，然后加：

```text
本次只执行“阶段 1：品牌和应用壳收敛”。
先不要修改 TRAE 认证、storage.json 解析、账号注入、进程管理和 GitHub 逻辑。
```

完成后由你运行验证并提交。

### 第二个 GLM 对话：阶段 2

开启新对话，仍让它读取同一份 Markdown，然后发送：

```text
本次只执行“阶段 2：Work CN 路径和安装发现兼容”。
阶段 1 已完成。先检查当前 Git 历史和现有代码，不要重做阶段 1。
```

后续阶段同理。

## 为什么建议每阶段新开对话

- 避免上下文过长后 GLM 忘记约束；
- 避免它顺手实现后续功能；
- 每次只需理解少量文件；
- 出错时容易定位到某个提交；
- 可以把上一个阶段的真实代码作为事实，而不是依赖聊天记忆。

## 原 Cockpit Tools 的使用规则

原程序：

```text
C:\Users\10156\AppData\Local\Cockpit Tools\cockpit-tools.exe
```

可以用于观察原作者的交互和切号效果，但：

- 禁止把开发源码放进安装目录；
- 禁止用开发构建覆盖 `cockpit-tools.exe`；
- 禁止直接编辑安装目录中的资源；
- 手工测试 Work CN 切号时，关闭原 Cockpit Tools，避免两个管理器同时修改 Work CN 的 `storage.json`；
- 开发版使用独立数据目录，不与原 Cockpit Tools 共用 `.antigravity_cockpit`。

## 如果 GLM 想一次做完

立即回复：

```text
停止。不要实现后续阶段。撤销所有不属于当前阶段的改动，只保留当前阶段要求；重新运行当前阶段验证并报告 git diff。
```

## 如果 GLM 只改了 crates/cockpit-core

回复：

```text
桌面应用实际使用 src-tauri/src/modules 下的模块。请检查本次修改是否只落在 crates/cockpit-core；如果是，撤销无效改动，并根据文档修改桌面实际编译路径，同时补对应测试。
```

## 如果 GLM 声称完成但没提供命令结果

回复：

```text
不要声称完成。请实际运行本阶段要求的 typecheck、build、Rust tests，并提供退出码和失败数量；再提供 git status、git diff --stat。没有真实验证证据不得结束。
```

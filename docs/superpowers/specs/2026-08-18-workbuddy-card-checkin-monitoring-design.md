# WorkBuddy 卡片、云端签到与按需监测设计

**日期：** 2026-08-18  
**状态：** 已确认，待实施计划  
**范围：** 桌面端 WorkBuddy/TRAE 账号卡片、云端签到页、WorkBuddy 监测生命周期、GitHub 同步状态；云签到仓库仅做本地代码与测试，不自动推送远端。

## 目标

1. WorkBuddy 本地账号卡片以现有 TRAE 卡片为视觉基准，统一尺寸、间距、信息层级和操作区。
2. TRAE 与 WorkBuddy 的本地卡片、云端签到卡片均显示 UID，并合理利用固定卡片空间。
3. 云端签到继续保留一个入口，但不再把两种产品的状态和操作无差别混合。
4. WorkBuddy 未被用户查看时不进行无意义的安装检测和页面轮询。
5. 修复 WorkBuddy 卡片笼统显示“GitHub 失败”的状态语义，保留可重试、可解释的真实同步结果。

## 非目标

- 不把 TRAE 与 WorkBuddy 的业务流程强行抽象成完全相同的实现。
- 不改变 WorkBuddy 官方登录、账号快照和切换事务的安全边界。
- 不在本次工作中自动推送云签到仓库或修改 GitHub 线上状态。
- 不在前端暴露 access token、refresh token、认证文件原文或完整手机号。

## 现状与根因

### 卡片不一致

WorkBuddy 本地页复用了部分 `wc-slot` 样式，但额外引入独立的产品标题、GitHub 状态和详情网格；云端签到又分别实现 `CredentialCard` 与 `WorkBuddyCheckinCard`。三套结构的字段顺序、卡片高度、操作区和响应式规则不同，因此视觉上无法真正一致。

### WorkBuddy 检测过于频繁

当前存在两层重复检测：

- Tauri 启动阶段无条件启动 WorkBuddy 会话监测器，启动 10 秒后首次扫描，之后每 60 秒扫描。
- `WorkBuddyPage` 每次挂载立即检测安装和加载账号，并每 30 秒重复读取安装、账号和监测状态。

页面由条件渲染切换，离开后会卸载、重新进入又会重新挂载，因此切页会重复触发检测。

### GitHub 失败缺少真实语义

导入或修改 WorkBuddy 账号时会自动调用聚合同步，但调用方丢弃错误。同步函数在配置未完成、凭证构建失败和远端命令失败时都把所有账号统一标记为 `failed`，账号模型又只保存状态和时间，不保存脱敏失败原因。因此用户只能看到“GitHub 失败”，无法判断是尚未配置、待部署还是实际远端失败。

此外，云签到仓库中的 `WORKBUDDY_ACCOUNTS_JSON` 解析和工作流环境映射目前只存在于本地未提交改动，线上工作流仍使用旧的 `WB1_TOKEN`、`WB2_TOKEN` 契约。

## 方案选择

采用“统一视觉骨架、保留产品适配层”的方案。

- 共享卡片布局、身份行、状态区域、操作区和响应式样式。
- TRAE 与 WorkBuddy 各自保留数据获取、刷新、签到和同步动作。
- 不创建充满产品条件分支的单一万能组件；只抽取稳定且真正相同的展示模型与小组件。

该方案比单纯调整 CSS 更能防止后续继续分叉，也比完全通用组件更符合两种产品不同的业务流程。

## 界面设计

### 本地账号页

TRAE 与 WorkBuddy 卡片使用相同的网格列宽、最小高度、内边距、圆角、阴影、标题行和底部操作区。

卡片从上到下分为：

1. 标题行：账号显示名、当前账号徽标及紧凑状态。
2. 身份行：脱敏邮箱或手机号，以及 `UID`。UID 过长时中间省略，完整值放在 `title` 中。
3. 数据区：使用稳定的两列网格承载令牌有效期、积分、今日奖励、连续签到或 TRAE 对应摘要。
4. 状态区：只在有必要时显示凭证、同步或查询异常，不为正常状态长期占用额外高度。
5. 操作区：固定在卡片底部，按钮顺序和换行规则一致。

WorkBuddy 保留“参与自动签到”“切换并打开”“刷新状态”“立即签到”“备注”“删除”等专属操作。TRAE 保留自己的刷新、同步和切换动作，但展示密度与 WorkBuddy 对齐。

### 云端签到页

云端签到仍为单一入口，顶部使用 `全部 / TRAE / WorkBuddy` 分段控件。

- `全部`：按 TRAE、WorkBuddy 分为两个有标题的账号组，不混排为一个无产品边界的列表。
- `TRAE`：仅显示 TRAE 账号、同步和验证操作。
- `WorkBuddy`：仅显示 WorkBuddy 账号、聚合同步和按账号签到操作。

云端卡片与本地卡片使用相同视觉骨架，并统一显示产品、账号名和 UID。产品特有的 token、积分、槽位、自动签到和本地诊断状态通过适配模型填入对应区域。

页面顶部不再长期显示只适用于 TRAE 的全局验证按钮。产品级命令随当前筛选切换；需要指定账号的操作保留在账号卡片内。

运行历史仍可共享，但必须在可识别时标注产品；无法从工作流标题识别时显示“通用任务”，不猜测来源。

## 监测生命周期

### 启动策略

应用启动时不再无条件启动 WorkBuddy 会话监测器。

监测只在以下场景首次激活：

- 用户进入 WorkBuddy 页面。
- 用户进入云端签到并实际查看包含 WorkBuddy 的内容。

前端通过显式命令激活监测。后端保证同一进程只启动一个监测任务，重复激活是幂等操作。

### 前端刷新策略

删除 WorkBuddy 页面每 30 秒执行的安装检测、账号加载和会话状态轮询。

安装状态仅在以下时机刷新：

- 当前应用会话首次进入 WorkBuddy 页面。
- 用户点击“重新检测”。
- 修改 WorkBuddy 路径成功。
- 导入、切换或强制关闭切换完成。

账号列表通过 Store 的会话级 `loaded` 状态避免切页重进重复加载。账号发生导入、修改、删除或切换后按需刷新。

### 后端监测策略

监测器激活后保留低成本的文件元数据检查。认证文件修改时间未变化时：

- 不读取认证文件正文。
- 不解析 token。
- 不请求积分。
- 不访问 GitHub。

只有文件确实发生变化时才稳定读取并更新本地加密快照。自动签到已启用且 token 变化时，才进入防抖 GitHub 同步。

## GitHub 同步状态模型

WorkBuddy GitHub 状态改为明确的有限状态：

- `pending`：账号或 token 已变化，但配置未完成或尚未执行 Secret 同步。
- `syncing`：正在执行聚合 Secret 同步。
- `synced`：最近一次远端同步成功。
- `failed`：真正执行 GitHub 命令后失败。

账号视图增加可选的脱敏失败原因。错误不得包含 token、Secret 原文、认证 JSON、完整手机号或命令 stdin。

配置未启用或仓库为空时不标记为 `failed`，显示“待同步”。远端工作流是否已经部署 WorkBuddy 契约与 Secret 同步状态分开处理，不把“工作流尚未部署”伪装成账号同步失败。

导入、切换、修改自动签到和删除操作不因 GitHub 失败回滚本地结果，但必须把同步结果返回前端：

- 本地成功、远端成功：显示成功提示。
- 本地成功、远端待处理：显示待同步提示。
- 本地成功、远端失败：显示脱敏原因和重试入口。

云端签到页作为主要同步与重试入口；WorkBuddy 本地卡片保留紧凑状态，避免用户失去账号同步是否成功的可见性。

## 云签到仓库契约

本地云签到仓库继续实现以下兼容契约：

- 优先读取版本化的 `WORKBUDDY_ACCOUNTS_JSON`。
- 每个账号包含稳定键、清理后的显示名和 access token。
- 合法聚合 Secret 覆盖旧 `WB1_TOKEN`、`WB2_TOKEN`。
- 聚合 Secret 缺失时回退旧变量；合法空数组不回退。
- `account_filter=workbuddy:<stable-key>` 按稳定键筛选单账号。
- 工作流显式映射 `WORKBUDDY_ACCOUNTS_JSON`。

实现和测试只保留在本地仓库。完成后报告待提交、待推送文件，不自动修改远端仓库、Secret 或工作流。

桌面端卡片的 `synced` 仅表示聚合 Secret 已成功写入 GitHub，不代表远端工作流已经包含 `WORKBUDDY_ACCOUNTS_JSON` 环境映射。工作流部署状态在云端签到页或最终交付说明中独立提示。

## 错误处理

- 页面首次加载失败不覆盖已经缓存的可用账号。
- 单个 WorkBuddy 状态查询失败只影响对应卡片。
- GitHub 自动同步失败必须写入脱敏日志并返回结构化错误，不再静默丢弃。
- 云端签到的 TRAE 与 WorkBuddy 操作分别维护 loading 和错误状态，互不阻塞。
- 页面离开后忽略已经失效的异步 UI 更新，避免切页后弹出过期反馈。

## 测试策略

### 前端

- 纯函数测试：标题、UID、省略文本、产品标签、GitHub 状态映射和 `全部` 分组顺序。
- Store 测试：同一应用会话只加载一次、切页重进不重复检测、操作完成后按需刷新。
- 页面测试：TRAE 与 WorkBuddy 卡片具有相同结构槽位；两者均展示 UID；产品筛选只显示对应操作。
- 响应式验证：桌面和窄窗口下按钮不溢出，文本不遮挡，卡片网格稳定。

### Rust

- 未配置 GitHub 时状态为 `pending`，不为 `failed`。
- 真正远端失败时保存 `failed` 和脱敏原因。
- 同步成功后清除旧错误并写入 `synced`。
- 监测器未激活时不扫描；重复激活只启动一个任务。
- 文件元数据未变化时不读取认证内容、不触发 GitHub。

### 云签到仓库

- 聚合 Secret 优先级、合法空数组、错误回退、去重和稳定顺序。
- WorkBuddy 稳定键筛选及旧账号变量兼容。
- 工作流包含聚合 Secret 环境映射。

### 完整验证

- 运行前端单元测试、TypeScript 类型检查和 Vite 构建。
- 运行 WorkBuddy 相关 Rust 定向测试，并在风险允许时运行完整 Rust 测试。
- 运行云签到 Python 测试。
- 启动本地界面，使用桌面与窄窗口截图核对卡片、UID、产品分组和操作换行。
- 使用 `git diff --check` 检查空白错误，并明确列出未推送的远端改动。

## 验收标准

1. WorkBuddy 与 TRAE 本地卡片在同一窗口宽度下具有一致的视觉结构和响应式行为。
2. TRAE 与 WorkBuddy 的本地、云端卡片都显示 UID，且长 UID 不破坏布局。
3. 云端签到的 `全部` 视图按产品分组，产品筛选只展示对应命令。
4. 未进入 WorkBuddy 或包含 WorkBuddy 的云端签到视图前，不启动 WorkBuddy 扫描。
5. WorkBuddy 页面不存在 30 秒全量轮询。
6. 配置未完成显示“待同步”，真实远端失败才显示“GitHub 失败”及脱敏原因。
7. 本地导入、切换和删除不因 GitHub 故障回滚。
8. 所有自动化验证通过；无法执行的真实远端验证有明确说明。
